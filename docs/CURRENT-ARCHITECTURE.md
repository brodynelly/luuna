# Current Luuna architecture

Windows native development startup invokes a fixed local bootstrap command,
starts or authenticates/reuses the independent runtime and connects without
manual token entry. DPAPI records live in `%USERPROFILE%\.luuna\credentials`;
existing encrypted LocalAppData records migrate once without deleting them.
Tokens reach the view through local IPC and stay in memory. Closing the window
leaves the service running. See [ADR 0011](decisions/0011-windows-native-bootstrap.md)
for the command boundary, reconciliation and checkout-based distribution limits.

Date: 2026-10-16, updated 2026-10-17 for M2a, M2b, M2c and the M3 implementation, and 2026-10-21 for re-validation after a review that left no verdict, shutdown interruption, client hardening the desktop design system and explicit component runtime workflows. Status: authoritative foundation baseline; implementation evidence is required for each milestone.

## Purpose and precedence

Luuna is a local-first development workbench for one developer working across related repositories. Its runtime coordinates scoped Pi sessions, exact-plan approval, actual checks, independent review, durable evidence, and eventually linked pull requests. The developer decides when to merge.

For new work, apply the following order:

1. Explicit current user requirements and repository-wide safety/security rules.
2. This document and accepted records in `docs/decisions/`; a later accepted decision must update this summary.
3. `docs/02-requirements.md` for full-v1 functional requirements not explicitly revised here.
4. The desktop/Pi RPC proposal for detailed design rationale.
5. The numbered design chapters, complete reference reading copies, diagrams, and examples as historical material.

README and AI-START-HERE are entry points, not alternative specifications. Existing source and tests show implemented behavior; they do not silently override a requirement. When an implementation differs, record the gap or an explicit decision.

## Delivery and boundaries

Runtime I/O isolation and bounded session history follow
[ADR 0015](decisions/0015-bounded-runtime-and-history.md): synchronous transactions
run under bounded blocking admission, SSE reads in pages, and the desktop keeps
a bounded live event window with on-demand historical navigation. Check progress
is lossy display data; private artifacts and durable runtime events remain the
evidence. Windows check processes join owned Job Objects before execution.

The initial client is Tauri 2 with React and TypeScript. An independent Rust service uses Tokio, an authenticated Axum API, and local SQLite persistence. Pi RPC subprocesses execute agent assignments. A client cannot directly authorize tools or decide that validation succeeded.

```text
Tauri/React client ── authenticated HTTP + resumable SSE ── Rust runtime
                                                          ├── SQLite + private artifacts
                                                          ├── supervised Pi RPC workers
                                                          ├── Git/worktree ownership
                                                          ├── deterministic check executor
                                                          └── versioned external adapters
```

Desktop-first is a sequencing decision. Browser/TUI capability parity, multiple related repositories, scoped memory, and Mac/Windows support remain full-v1 obligations. They are not exit criteria for the first single-repository foundation demo. No hosted service, mandatory NAS, GPU, automatic merge, custom agent loop, or full IDE replacement is required.

The desktop client's presentation follows one token-based design system ([ADR 0013](decisions/0013-desktop-design-system.md), [DESIGN-SYSTEM.md](DESIGN-SYSTEM.md)): six outcome tones mapped from the API unions, where only passed evidence is green and interruption is never failure, both colour schemes and WCAG AA enforced by tests. It changes how runtime state is shown, never what the runtime decides.

Client parity (R02, A33) follows one capability catalog ([ADR 0020](decisions/0020-capability-catalog-and-tui.md)): `schemas/capability-catalog.json` lists every product action with its runtime route, `@luuna/api-client` method, desktop control marker and TUI command; `scripts/check-contracts.mjs` validates it against the runtime's served routes and the typed client. The failure explanations (`packages/api-client/src/failures.ts`) are shared by the desktop and the terminal client `packages/tui` (`luuna-tui`, interactive menus and a scriptable non-interactive mode, SSE event following with resumption, hidden token entry, full-hash approval acknowledgment). Parity evidence: the TUI command test, the desktop marker test and `scripts/tui-smoke.mjs`. Actions still arriving from M4/M5/M7 join the catalog as they land.

The workspace should add crates when they contain a real contract or implementation: domain, storage, runtime/API, engine/Pi, Git, executor, validation, and external adapters. Shared frontend packages are created when an actual shared consumer needs them. Empty placeholders do not establish implementation progress.

## Runtime ownership

Only the Rust runtime may enforce state transitions, immutable plan hashes, approval scope, execution permissions, task dependencies, limits, retries, candidate identity, check evidence, review acceptance, and publication gates. Agents provide proposals and worker output. Deterministic runtime code produces authoritative domain events.

An approval binds to the complete canonical executable plan, its revision and hash, repository scope, base commits, check recipes, resource profiles, and budgets. Feature implementation requires a valid approval and a passing baseline. New code, rebases, dependency changes, and manual edits invalidate affected evidence. Review and publication refer to exact candidates; model text saying “passed” is never command evidence. The desktop displays the entire immutable plan and full hash and requires acknowledgment before enabling approval. Managed Git checkout, status, staging and commit disable configured clean, smudge and process filters with per-command overrides; these operations do not authorize repository-configured commands.

Native execution uses host permissions. Stronger isolation requires an explicitly configured execution profile with actual operating-system or container boundaries. Preserve developer changes and only clean up resources whose Luuna ownership is verified.

## Persistence and ticket authority

SQLite owns Luuna projects, immutable plan revisions, approvals, run/attempt lifecycle, sequenced events, check/review evidence, artifact references, and publication reconciliation. State mutation and emitted durable domain events must be committed consistently. Sensitive transcripts and provider data remain private artifacts with controlled access and retention.

The schema is versioned and append-only. At startup the runtime refuses a database that fails SQLite's quick check or was written by a newer schema, before writing anything to it. It applies only missing migrations, after an automatic pre-migration snapshot under `<data>/backups/`. `luuna-runtime backup` takes a consistent online snapshot. `luuna-runtime restore` needs the runtime stopped, verifies the snapshot, and moves the current database and its `-wal`/`-shm` aside before installing it. `luuna-runtime check` reports integrity and schema version. A snapshot covers the database only; artifacts and worktrees are files, so a complete backup is the data directory copied after an orderly stop. Startup recovery skips records it cannot decode, logs them by table and ID, and still settles their state where it can. See [ADR 0016](decisions/0016-storage-backup-and-schema-compatibility.md).

Baselines are runs: `POST /api/v1/projects/{id}/baselines` executes a repository's confirmed required recipes through the supervised executor and records `CheckResult` evidence bound to the manifest hash, exact commit and tree, and an environment fingerprint, with private hashed artifacts. `Implementing` is entered only through the transactional gate that re-checks the approval, the current manifest and a passed matching baseline per repository; see [ADR 0007](decisions/0007-baseline-executor.md). One baseline per repository runs at a time. Every check's process group is recorded; whatever a check leaves running is terminated before its result is recorded, and startup recovery terminates verified survivors of checks a hard-killed runtime left behind (Windows checks run in kill-on-close job objects). Missing tools or dependencies and checks cut short by the workflow budget are blocked infrastructure, never failures a repair is asked to fix (ADR 0007 amendment, 2026-10-21).

A repository whose settled baseline shows no usable testing setup (no required check in the manifest, or every required check exiting 0 while its recognised runner counted no executed test: an empty or skip-only suite; a missing tool, a dirty checkout or a failed check is not this case) is offered the prerequisite of docs/08-validation.md: the offer is a structured `TestingPrerequisite` recorded on the baseline run (`baseline.prerequisite_offered`), returned as `prerequisite` on the baselines list, as `prerequisites` on `GET /api/v1/projects/{id}` and in the 422 body that refuses `implement` for an approved feature plan on that repository. Tickets and plans carry a hashed `purpose` (`feature`, the omitted default, or `testing_setup`). A `testing_setup` plan has one task with the `testing-setup` role (`agents/testing-setup.md` reaches the writer verbatim) and proposes the recipes that will become the baseline (`checks` on `POST /api/v1/tickets/{id}/plans`, validated as manifest checks; absent, the manifest's required recipes), and `POST /api/v1/runs/{id}/implement` admits it without a passing baseline under every other gate (approval, bindings, base commit, free repository, budgets, host fingerprint computed for the proposed recipes); its candidate runs those recipes in the owned worktree and cannot pass unless at least one recognised runner counted an executed test, then is reviewed as any candidate. The handoff is explicit and the developer's: `GET …/candidate` names it (merge the reviewed candidate, confirm the next manifest revision with the checks, run a normal baseline); feature plans stay refused until that baseline passes, and tests a feature candidate writes are never the prerequisite. See [ADR 0022](decisions/0022-testing-setup-prerequisite.md).

Projects are registered from existing repositories. The confirmed **project manifest** (`schemas/project.schema.json`, hashed with `luuna-json-v1`) is machine-independent and append-only by revision; the **machine registry** maps each repository ID to its local path and the identity observed at registration (the redacted configured remote plus the root commits reachable from HEAD). A later observation must show an equivalent remote and contain those roots; only an explicit, evented rebind changes a binding. A checkout is registered once and never overlaps the runtime data directory. Discovery proposals and project-scoped events (`project.registered`, `repository.registered`, `repository.rebound`, `discovery.proposed`, `manifest.confirmed`) are durable, and replaying the project stream reconstructs the confirmed map. Inspection never writes to a repository or executes its text, including filters configured in submodules; see [ADR 0006](decisions/0006-repository-import.md).

Discovery also probes the host once per proposal (`Discovery.host_capabilities`: each profile tool resolved on `PATH` and asked only for its version) and annotates every proposed check with `capability: available | missing` and its missing tools, raising a `missing-tool` question rather than dropping the recipe; a confirmed check whose tool is absent is recorded `blocked`, never `failed`. Every advertised profile (Node, React, Next.js, TypeScript, Go, Python, Rust, Flutter, native Android, native iOS) proposes real recipes; iOS and Android device recipes carry capabilities (`xcode`, `android-device`) this host cannot satisfy and say so. New projects are created only through a hashed `ScaffoldProposal` (`POST /api/v1/projects/scaffold/propose`: files, baseline recipes, generator and network steps, tool probes, `ready | blocked`) that the developer confirms by exact hash (`POST /api/v1/projects/scaffold`): the runtime writes the files, commits, runs the baseline recipe through the supervised executor as a real check, registers the project and records `project.scaffolded`; a failing baseline is returned as such and never reported passing. Android and iOS scaffolds are blocked proposals naming their platform generators. React and Next.js (`nextjs`, a written-out minimal App Router template with TypeScript and Vitest rather than `create-next-app`) are complete offline templates whose `npm install` is a declared network step: without `confirm_network` the scaffold is refused and names the step, with it the install runs under the supervised executor before the baseline. A proposal's `notes` state the limits the developer accepts with its hash, such as the Node TypeScript template's typecheck gap (Node's built-in type stripping runs the tests without checking types until `typescript` and a `typecheck` script are added). See [ADR 0019](decisions/0019-stack-profiles-and-scaffolding.md); capable-runner evidence for Go, Flutter, Android and iOS remains open, and the Next.js baseline has not run on a networked host.

Legacy projects retain the explicitly temporary SQLite ticket source until component activation. `POST /api/v1/projects/{id}/components` durably initializes the private component workspace and migrates tickets while preserving IDs and numeric revisions. Enabled projects use Missions (Seeds-derived) as authority for ticket intent, acceptance criteria, status, dependencies and source fingerprints; SQLite stores its revision-aware projection and Luuna execution state. GET/list return the last reconciled projection; `GET /api/v1/tickets/{id}/source` reports actual source freshness and `POST /api/v1/tickets/{id}/reconcile` requires the expected projection revision. External edits advance the reconciled revision and invalidate stale plans; freshness, ticket readiness and dependencies are rechecked at runtime work/evidence boundaries. Missing components fail closed. There are never two independently writable authorities for these fields. See [ADR 0003](decisions/0003-ticket-authority.md) and [ADR 0014](decisions/0014-runtime-component-workflows.md).

## Pi and maintained components

Pi is the agent engine, not the scheduler or validation authority. The engine contract supervises process creation, assignments, followups, events, stop requests, inspection, and disposal. Use a tested pinned release, strict JSONL framing, command correlation, bounded buffers, timeouts, and owned child-process cleanup. Stderr is diagnostic data. Prompt acceptance and agent settlement are separate events. Persist attempts so interrupted processes cannot become successful runs after restart.

Luuna maintains three branded CLI distributions: **Missions** (`@luuna/missions-cli`, Seeds-derived), **Atlas** (`@luuna/atlas-cli`, Mulch-derived), and **Beacon** (`@luuna/beacon-cli`, Canopy-derived). They live under `components/missions`, `components/atlas`, and `components/beacon` as separate package and integration boundaries. Preserve compatible underlying APIs/data formats, upstream copyright and MIT notices. Prefer adapters over rewrites or direct SQLite access to their records.

The owner resumed extraction on October 21, 2026 and explicitly authorized public component repositories. Missions, Atlas and Beacon now live in `brodynelly/luuna-missions`, `brodynelly/luuna-atlas` and `brodynelly/luuna-beacon`; Luuna stays private and consumes exact-commit Git submodules at the existing components paths. The manifest and gitlinks bind dependency identity; setup uses frozen Bun locks without lifecycle scripts, and consumer smoke checks exercise real CLI/JSON operations. Each destination owns its CI and source; registry packages remain private and unpublished. See [ADR 0012](decisions/0012-independent-component-repositories.md), superseding ADR 0002's hosted-extraction deferral.

The runtime now invokes these pinned CLIs through `luuna-components` with bounded input/output, a fixed stdin bridge, isolated HOME/config, sanitized environment, source/toolchain verification and owned process cleanup. Explicit per-project activation uses `<data_dir>/components/projects/<id>`; explicit user memory uses `<data_dir>/components/user`. It never adopts developer or imported stores. Atlas memory exposes explicit scope and provenance; Beacon exposes versioned prompt preview/update. A user selects resources for a plan, whose canonical optional `component_context` contains their exact snapshots, identities and hashes. The runtime rejects changed selected sources at approval and execution/evidence boundaries and gives workers only approved bounded content. Durable intent ledgers reconcile uncertain component writes before retry. Imported development metadata is not runtime data or permission to load instructions into agents. See [ADR 0014](decisions/0014-runtime-component-workflows.md) for activation, ticket reconciliation, resource selection and native-process limits. Memory promotion widens scope one step at a time (`process -> project -> user`) through `POST …/memory/{id}/promote` with the displayed hash, creating the wider record with provenance naming its origin and deleting the narrower one under the same intent ledger; `GET /api/v1/projects/{id}/export` returns the manifest, ticket projections, project and process memory and current prompts, and is refused outright when it would carry user memory, a credential value or a path of this host ([ADR 0021](decisions/0021-memory-promotion-and-project-export.md)). Import of an export, retention policy and supported-platform evidence remain obligations.

## Candidate validation and review

Migration 5 stores exact candidate commit/tree identities, append-only validation generations and structured independent reviews. `POST /api/v1/runs/{id}/validate` names the expected hash and optionally `auto_repair`; it executes the approved required recipes inside the owned candidate worktree and starts a fresh read-only Pi reviewer only after the checks pass. Checks and reviews cannot be reused across candidate revisions or interrupted generations. A `failed` candidate whose required checks all passed in its current generation and whose reviewer left no verdict (invalid or self-inconsistent output, a refused session) may re-enter validation in place as generation `n+1`: same revision, approval and budgets, fresh checks and a fresh reviewer, no writer attempt; `GET …/candidate` reports that decision as `revalidate_allowed`. `GET …/candidate` and `GET …/diff` expose authoritative evidence and exact diffs; `POST …/repair` rechecks current approval, baseline/host and remaining aggregate budgets before creating the next scoped candidate. Model output never supplies command evidence. Repair writers receive the previous candidate's reason, check records, review and a bounded tail of each failed check log, never the private artifact paths. See [ADR 0009](decisions/0009-candidate-validation-review.md).

Since the second 2026-10-21 amendment to ADR 0009, every validation generation starts from the candidate tree alone: the owned worktree is verified and its untracked and ignored paths are removed and recorded. Content drift fails the candidate with a reason naming the change and the next step and is never re-validated in place. Review diffs ignore attributes that hide changes and are bounded with every changed path listed; a non-passing review must name a finding; reviewer tool calls are recorded by tool and path. `GET …/candidate` reports `validate_allowed` and `decision_reasons` from the gates the routes apply.

Automatic repair is opt-in and bounded by both the immutable plan and project repair policy. Infrastructure errors stop without repeated edits. Interrupted check and review stages retain elapsed usage up to their last durable heartbeat; a reviewer interrupted after its durable prompt marker, and every interrupted writer, reserve unknown spend and require re-planning when headroom is exhausted. Clients see aggregate workflow usage against the plan budgets and cumulative per-ticket usage, including spend the provider reported without a price. Review success is evidence for an exact candidate only; publication and human-controlled merge remain separate gates.

## Multi-repository coordination

A plan may carry several tasks, each on a distinct registered repository, with `depends_on` naming the tasks that must complete first; the contract refuses self, unknown, duplicate and cyclic dependencies by name, and bounds `budgets.max_workers` to the task count and the runtime's four-run limit. Discovery proposes `package` relationships between registered repositories from `package.json` dependencies, `Cargo.toml` path dependencies and `go.mod` replace directives with evidence and `confirmed: false`; confirming a manifest that still lists an unconfirmed relationship is refused, and confirmed relationships must be acyclic. `POST /api/v1/runs/{id}/implement` on such a plan runs the task graph: after the same gates as one writer (with one environment fingerprint per repository), tasks whose dependencies completed run concurrently up to `max_workers`, never two writers in one repository, each as a writer attempt in its own owned worktree, with every completed producer bound into the consumer's writer environment and prompt as `LUUNA_DEPENDENCY_<REPOSITORY>_PATH`/`…_COMMIT`. Per-task state is durable (migration 10, `GET …/tasks`, `task.*` events); a dependency's failure blocks its dependents with the reason, cancellation records every task, a restart marks running tasks interrupted and keeps completed commits and worktrees, and `implement` with `task_id` resumes a failed, blocked or interrupted task under the original approval within the approved budgets (an attempt lost mid-prompt still reserves the remaining cost budget, so re-planning follows as for one writer). When every task completed, one candidate set freezes every repository's exact commit and the `<consumer>:<producer>` bindings; validation runs every repository's required recipes in its own candidate worktree with the same bindings, binds results to exact commits, fails the set naming the repository and recipe (`integration blocked`) when a consumer check fails, and gives the fresh reviewer one bounded combined diff. Repair of a multi-repository set is re-planning. See [ADR 0017](decisions/0017-multi-repository-coordination.md). Every task carries an explicit role (`implementer`, `repository_lead`, `project_orchestrator`): an advisory role reads only, receives its `agents/` contract as the system prompt and the recorded results of the advisory tasks it depends on as reference data, must leave its worktree unchanged (any change is a scope violation) and records a bounded structured advisory result (findings, proposed tasks, risks) on the task and attempt instead of a commit; a plan of advisory tasks only completes with no candidate, and a proposal becomes a task only through a new plan revision the developer approves, naming the advisory task in `derived_from_task` (no runtime-created child tasks). Each task row and its `task.assigned`/`task.*` events record the assignment trace (role, the approval that assigned it, `derived_from_task`, dependencies, the overrides naming it, the attempt), per R06. At plan creation the implementer graph is checked against the confirmed relationships: a confirmed `producer -> consumer` relationship between two task repositories requires the consumer task to depend on the producer task unless the hashed plan carries a justified `waive` entry in `dependency_overrides`, a dependency between repositories without a confirmed relationship requires a justified `add` entry, and an idle override is refused; refusals name the relationship and the override that would allow the plan, and the overrides are echoed on the plan, the task records, the task events and `GET …/candidate`. See [ADR 0023](decisions/0023-delegated-roles-and-dependency-overrides.md).

## Publication and host diagnostics

A `reviewed` candidate with a `passed` review may be published (`POST /api/v1/runs/{id}/publish` with the exact hash and an idempotency key) to GitHub only, by the repository's registered identity: the runtime pushes each repository's exact candidate commit to `luuna/<ticket>/<hash prefix>` and opens one pull request per repository against the manifest's default branch, linking them when there are several. Every external write is preceded by a durable intent (migration 11: `publications`, `publication_intents`) and looked up by its stable identity first (`git ls-remote` for the branch, the pull-request head for the PR), so a timeout after remote success, a partial publication and a replayed key never duplicate anything; `POST …/publication/reconcile` retries only steps the ledger does not show succeeded. `GET …/publication` refreshes CI (check runs and commit status) and merge observation under bounded timeouts; a failing CI is reported distinctly and changes no evidence, and `integrated` is set only when every pull request is observed merged by a person. There is no merge route or call; a test asserts it. The GitHub token (`LUUNA_GITHUB_TOKEN`) reaches Git only through scoped `GIT_CONFIG_*` headers and the REST client as a bearer header; only its presence is ever reported. Events: `publication.requested`, `publication.pushed`, `publication.pr_opened`, `publication.failed`, `publication.reconciled`, `publication.integrated`. `luuna-runtime doctor [--json]` reports Git, Python, Node, the pinned Pi probe, the data directory and database, token and credential presence by name, the service port, the component layout kind (source checkout or portable, with its root) and the Bun executable, exiting 1 when a required item is missing. Since the 2026-10-22 amendment to ADR 0018, publication and reconciliation are admitted only after the same authorization gate validation and repair use (the stored approval must authorize the latest plan revision; ticket and manifest bindings must hold), after the ticket revision and approved component context are re-resolved, after every repository's Luuna-owned worktree is verified to hold exactly the frozen candidate (drift after the review invalidates the candidate, `candidate.invalidated`, and the run leaves `reviewed`), and after a deterministic pre-push policy scan of the exact patch (`crates/luuna-runtime/src/policy.rs`: approved scope, credential-store paths, credential-shaped content, known runtime credential values; findings never carry values). Refusals are `publication.refused` events. See [ADR 0018](decisions/0018-publication-and-doctor.md); every publication test runs against a fake GitHub API and a local bare remote, so real GitHub evidence remains M7 exit work. `scripts/package-windows.ps1` builds an unsigned NSIS development installer carrying the desktop, the release runtime, the Windows helper scripts, the pinned Pi tree, the pinned Missions/Atlas/Beacon trees with Bun 1.4.3, and the terminal client (`packages/tui`, `@luuna/api-client`, the capability catalog, `Luuna Terminal.cmd`); the native bootstrap of ADR 0011 prefers that packaged layout when it is present beside the executable and the startup helper points the runtime at its components. Components ship as a *portable layout* ([ADR 0024](decisions/0024-portable-component-distribution.md)): `scripts/stage-components.mjs` verifies the pins against the gitlinks, installs each checkout with the frozen script-free Bun command, copies the trees without Git metadata and writes `components/dist-manifest.json` (pinned commit, deterministic tree digest and the Bun hash); `luuna-components` accepts that layout beside the executable or under `LUUNA_COMPONENTS_ROOT`, recomputes the digests at discovery and before every call, and refuses a mismatch by component name, while a source checkout keeps the Git-metadata verification of ADR 0012. The clean-machine installer test is documented in [PACKAGING.md](PACKAGING.md) and has not been executed; Node.js stays a host prerequisite.

## API and service lifetime

All application routes use `/api/v1`. Implemented project routes are `POST /api/v1/projects` (register existing repositories by absolute root path), `GET /api/v1/projects[/{id}]`, `POST /api/v1/projects/{id}/discover` (read-only proposal), `PUT /api/v1/projects/{id}/manifest` (confirm with `expected_revision`), `POST /api/v1/projects/{id}/repositories/{repository_id}/rebind` (explicitly re-point a moved or re-identified checkout) and `GET /api/v1/projects/{id}/events`. The canonical create-ticket route is **`POST /api/v1/projects/{id}/tickets`** (implemented in M2c with an idempotency key; enabled projects use the Missions authority of ADRs 0003/0014). Do not add a parallel `POST /api/v1/tickets` alias. Other operations address ticket, plan, and run identities: `POST /api/v1/tickets/{id}/plans` records the next immutable plan revision and opens its workflow run, `POST /api/v1/plans/{id}/approvals` approves one exact hash, `POST /api/v1/runs/{id}/implement` schedules the writer after transactional revalidation, and `GET /api/v1/runs/{id}/worktrees` and `/attempts` expose the Luuna-owned worktree leases and attempts (ADR 0008). Commands that can create work require idempotency; operations sensitive to stale state require expected revisions. SSE streams use durable event IDs/cursors for replay and deduplication. Artifacts use authorized IDs, never arbitrary request-supplied filesystem paths.

Bind the development service to loopback and authenticate protected API actions. A development launch may use an explicitly managed foreground process. The desktop reconnects to that service; closing a window or losing SSE does not decide run lifetime. Explicit shutdown stops or reconciles owned workers and persists interruption: since 2026-10-21 work stopped by Ctrl+C or SIGTERM is recorded `interrupted` (resumable after restart), never `cancelled`, and the client shows a lost runtime as an outage, reconnects by itself and reloads authoritative state when the runtime answers again. A Tauri child/sidecar alone does not prove independent lifetime. Platform-specific startup, supervision, token storage, and shutdown must be tested before distribution. See [ADR 0004](decisions/0004-service-lifecycle.md).

## Milestone evidence

Windows orderly service stop is `POST /api/v1/shutdown`, authenticated with the
existing bearer token. The runtime closes scheduling admission, drains admitted
mutation handlers, interrupts owned work and exits cleanly; window closure is
still only a client disconnect. Windows scripts reuse the DPAPI-encrypted token
and data directory across restart. See [ADR 0010](decisions/0010-authenticated-service-shutdown.md).

The initial tool-free connectivity slice exposes authenticated run creation/history, cursor event replay and SSE, and cancellation. M2a adds read-only repository import, discovery proposals and confirmed manifest revisions; M2b adds supervised baselines with bound evidence; M2c adds temporary local tickets, immutable plan revisions, exact-hash approvals, Luuna-owned worktree leases and one scoped writer whose candidate waits in `validating`. M3 adds candidate-bound required checks, a fresh read-only reviewer, structured findings, optional bounded automatic repairs and conservative restart recovery; its genuine-provider exit is closed on Linux (see the status report) while native Mac/Windows lifecycle evidence remains open. The bounded M6 component slice adds explicit Missions migration/reconciliation and selected Atlas/Beacon plan resources. Publication, broader M6 parity and supported-platform exits remain separate capabilities.
