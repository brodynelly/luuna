# Pilot measurements, October 22, 2026

The acceptance chapter ([11-acceptance.md](11-acceptance.md)) asks that time to
first project map, event delivery latency, log rendering with large output,
cancellation delay, task overhead, memory growth, model usage and recovery
success be measured on a real project, with numerical targets set after M1 and
revisited with the pilot, and that no benchmark claim be fabricated. This is
the first such pilot. It is reproducible with
`node scripts/pilot-measurements.mjs --runtime <luuna-runtime> --repository <checkout> --out <dir>`;
the sanitized report is [evidence/pilot-beacon-fixture-2026-10-22.json](evidence/pilot-beacon-fixture-2026-10-22.json).

**What it is and is not.** The project is a fresh clone of the Luuna Beacon
component (a Bun TypeScript project with 459 real tests across 36 files),
registered as a real checkout: identity, HEAD and dirty state observed, the
checkout never written. The manifest's checks are the repository's own
`bun install --frozen-lockfile` and `bun test`, plus an optional recipe
that prints a 2 MB log for the large-output measurement. The model is the
synthetic Pi fixture: the writer and reviewer are deterministic, so the
numbers measure Luuna's own overheads (observation, discovery, checks,
worktrees, events, recovery), never a provider's latency or cost. A
genuine-provider pilot repeats this script with `LUUNA_PI_PROVIDER` and
`LUUNA_PI_MODEL` set and the fixture variables unset; its model-usage and
wall-time rows are the ones still owed.

Host: Linux x64 container, Node v22.22.0, Rust 1.90 release
build, Bun 1.4.3 on PATH.

Reading the rows: `task_overhead_ms` is 0 because the writer's elapsed time
is charged in whole seconds and rounds above the sub-second wall time of the
synthetic attempt; the overhead is bounded by the implementation wall time
(worktree creation, the writer's session, the scope judgement and the
candidate commit together). Event latency is the runtime's timestamp against
the client's receipt on the same host clock over one SSE connection. Memory
is the runtime process's resident set from `/proc`, read before the pilot and
after the restart and the full workflow.

The recovery check kills the runtime with SIGKILL while the candidate's checks
run, restarts it on the same data directory, and finds the run and candidate
recorded as interrupted with nothing lost; the same candidate is then
validated fresh and reaches an independent review with the real test suite
passing in the Luuna-owned worktree.

## Targets

The chapter asks for targets to be set after M1 and revisited here. On this
evidence the proposed v1 targets for a local runtime on a developer machine
are: first project map under 3 s for a single repository; event delivery
median under 250 ms; a 2 MB log served under 100 ms; cancellation under 1 s;
runtime restart under 1 s with every run durable; resident memory growth
under 50 MiB across a full workflow. Every row above is inside these targets
on this host. They remain proposals until a genuine-provider pilot on a Mac
or Windows developer machine confirms them (RELEASE-EVIDENCE.md, still
blocked list).
