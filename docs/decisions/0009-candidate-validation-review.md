# ADR 0009: candidate-bound checks, independent review and bounded repair

Date: 2026-10-17. Status: accepted; amended 2026-10-17 (repair feedback content, genuine-provider evidence).

## Context

M2c freezes an approved writer's candidate and stops in `validating`. R09 requires actual required checks plus a fresh independent review; R10 requires durable bounded repairs and useful recovery. A model's self-assessment cannot establish either gate.

## Decision

1. **Freeze candidate evidence.** Migration 5 records each candidate's exact commits, repository trees, approved plan hash, writer attempt identity and sequential revision. Required command results and structured reviews bind to that exact candidate. Old candidate revisions and validation generations remain audit records. Generic run transitions cannot enter validation/review success or bypass the implementation/repair gates.
2. **Explicit candidate validation.** `POST /api/v1/runs/{id}/validate` names the expected candidate hash and reviewer provider/model (or configured defaults). The runtime claims the durable stage once, verifies the owned worktree and its HEAD/tree/tracked content, executes the immutable plan's required recipes through `luuna-executor`, records hashed private artifacts and checks identity again before accepting results. Optional or missing checks cannot satisfy the gate; infrastructure/empty-suite failures are blocked separately from assertion failures. Build output may be untracked; tracked mutation or a moved HEAD fails. Artifact identities include candidate revision and validation generation so a repair/retry cannot overwrite old logs.
3. **Independent review is a fresh Pi process.** Only after all required checks pass does the runtime enter `reviewing`. The new isolated configuration has fixed read-only file tools and a read-only scope guard. Its context contains requirements, exact diff/current code and runtime check evidence, without the writer conversation, Pi history or personal context. Output must deserialize to `ReviewResult` and name the exact candidate and assigned reviewer session; the runtime assigns the review record ID. Blocking findings cannot pass. Invalid JSON, model/transport errors, cancellation, timeout and post-review candidate drift fail closed. Diffs disable external drivers, text conversion and content filters.
4. **Repair is separately gated reuse of an existing approval.** `POST /api/v1/runs/{id}/repair` names the exact failed/paused candidate. It rechecks current approval, ticket/manifest/base binding, host-matching passed baseline, repository identity/HEAD, remaining attempts/time/cost and confirmed `max_task_repairs`. A new scoped writer starts in a new owned worktree from the preceding candidate commit, with recorded check/review feedback: the previous reason, check records, structured review and a bounded tail (2 KiB per artifact, 16 KiB encoded in aggregate, at most 32 artifacts and 64 MiB read) of each failed check's private stdout/stderr log with configured credential values redacted and private-key/token shapes removed best effort (native checks keep host permissions, so the developer-confirmed manifest remains the boundary on what a check may read), because the writer has no shell and the first genuine-provider run showed a repair writer that only saw an exit code guessing wrong. It creates the next candidate revision; prior checks/review never authorize that revision. Validation may opt into `auto_repair`; ordinary nonzero check exits and `changes_required` reviews then run bounded repair/check/review cycles under one cancellable active operation. Missing infrastructure, signals, deadlines, drift, transport errors or invalid model output stop without automatic edits. Exhaustion pauses with retained evidence and a re-plan recommendation. Manual repair remains available through the same gates. No implicit publication occurs.
5. **Accounting and restart are durable.** Writer attempts plus validation/review usage share the approved aggregate budgets. Per-message model cost is accumulated once, including multi-turn reviews. Interrupted checks preserve elapsed time from durable stage checkpoints and require a fresh validation generation. Interrupted model stages have unknown final provider spend: recovery conservatively reserves the remaining approved cost budget and requires re-planning rather than granting fresh budget. Worktrees, check artifacts and previous evidence remain intact. Native execution retains host permissions; no OS isolation is claimed.
6. **Clients display runtime evidence.** Candidate/diff endpoints expose exact identity, check results, findings, failure reasons and permitted repair availability. Controls use active work status; an idle `validating` candidate has no process to cancel. A reviewed candidate is evidence for its exact frozen identity, not permission to publish or merge.

## Evidence and remaining gates

Synthetic Pi fixtures make failure/recovery paths deterministic; required checks execute real host commands. Current platform and real-provider evidence are listed separately in `FOUNDATION-STATUS.md`, including the `scripts/m3-smoke.mjs` genuine-provider run (OpenRouter, pinned Pi 1.3.0) that closed the provider exit on Linux. Native Mac/Windows service lifecycle evidence remains open. Publication, merging, native service packaging, distributed clients and multi-repository scheduling remain later milestones. The developer controls merging.
