# ADR 0009: candidate-bound checks, independent review and bounded repair

Date: 2026-10-17. Status: accepted; amended 2026-10-17 (repair feedback content, genuine-provider evidence; developer decision that v1 ships no OS sandbox and keeps bounded, redacted repair feedback on by default) and 2026-10-21 (point 7: a fresh validation generation after a review that left no verdict).

## Context

M2c freezes an approved writer's candidate and stops in `validating`. R09 requires actual required checks plus a fresh independent review; R10 requires durable bounded repairs and useful recovery. A model's self-assessment cannot establish either gate.

## Decision

1. **Freeze candidate evidence.** Migration 5 records each candidate's exact commits, repository trees, approved plan hash, writer attempt identity and sequential revision. Required command results and structured reviews bind to that exact candidate. Old candidate revisions and validation generations remain audit records. Generic run transitions cannot enter validation/review success or bypass the implementation/repair gates.
2. **Explicit candidate validation.** `POST /api/v1/runs/{id}/validate` names the expected candidate hash and reviewer provider/model (or configured defaults). The runtime claims the durable stage once, verifies the owned worktree and its HEAD/tree/tracked content, executes the immutable plan's required recipes through `luuna-executor`, records hashed private artifacts and checks identity again before accepting results. Optional or missing checks cannot satisfy the gate; infrastructure/empty-suite failures are blocked separately from assertion failures. Build output may be untracked; tracked mutation or a moved HEAD fails. Artifact identities include candidate revision and validation generation so a repair/retry cannot overwrite old logs.
3. **Independent review is a fresh Pi process.** Only after all required checks pass does the runtime enter `reviewing`. The new isolated configuration has fixed read-only file tools and a read-only scope guard. Its context contains requirements, exact diff/current code and runtime check evidence, without the writer conversation, Pi history or personal context. Output must deserialize to `ReviewResult` and name the exact candidate and assigned reviewer session; the runtime assigns the review record ID. Blocking findings cannot pass. Invalid JSON, model/transport errors, cancellation, timeout and post-review candidate drift fail closed. Diffs disable external drivers, text conversion and content filters.
4. **Repair is separately gated reuse of an existing approval.** `POST /api/v1/runs/{id}/repair` names the exact failed/paused candidate. It rechecks current approval, ticket/manifest/base binding, host-matching passed baseline, repository identity/HEAD, remaining attempts/time/cost and confirmed `max_task_repairs`. A new scoped writer starts in a new owned worktree from the preceding candidate commit, with recorded check/review feedback: the previous reason, check records, structured review and a bounded tail (2 KiB per artifact, 16 KiB encoded in aggregate, at most 32 artifacts and 64 MiB read) of each failed check's private stdout/stderr log with configured credential values redacted and private-key/token shapes removed best effort (native checks keep host permissions, so the developer-confirmed manifest remains the boundary on what a check may read), because the writer has no shell and the first genuine-provider run showed a repair writer that only saw an exit code guessing wrong. It creates the next candidate revision; prior checks/review never authorize that revision. Validation may opt into `auto_repair`; ordinary nonzero check exits and `changes_required` reviews then run bounded repair/check/review cycles under one cancellable active operation. Missing infrastructure, signals, deadlines, drift, transport errors or invalid model output stop without automatic edits. Exhaustion pauses with retained evidence and a re-plan recommendation. Manual repair remains available through the same gates. No implicit publication occurs.
5. **Accounting and restart are durable.** Writer attempts plus validation/review usage share the approved aggregate budgets. Per-message model cost is accumulated once, including multi-turn reviews. Interrupted checks preserve elapsed time from durable stage checkpoints and require a fresh validation generation. Interrupted model stages have unknown final provider spend: recovery conservatively reserves the remaining approved cost budget and requires re-planning rather than granting fresh budget. Worktrees, check artifacts and previous evidence remain intact. Native execution retains host permissions; no OS isolation is claimed. Developer decision (2026-10-17, PR #5 review): v1 does not sandbox native checks, so repair feedback stays enabled by default, bounded and redacted as described above, with the developer-confirmed manifest as the boundary on what a check may read; an opt-in flag or sandbox is deferred beyond v1.
6. **Clients display runtime evidence.** Candidate/diff endpoints expose exact identity, check results, findings, failure reasons and permitted repair availability. Controls use active work status; an idle `validating` candidate has no process to cancel. A reviewed candidate is evidence for its exact frozen identity, not permission to publish or merge.
7. **A review that left no verdict costs a generation, not a revision (2026-10-21).** The genuine-provider runs showed small models violating the reviewer JSON contract after every required check had passed; the runtime failed those candidates closed, and the only recovery was a repair revision, which spent a writer attempt on a candidate nothing was wrong with. `POST /api/v1/runs/{id}/validate` therefore also accepts a `failed` candidate whose every required recipe has a passed result in its current validation generation and whose review is absent: invalid or self-inconsistent reviewer output, a refused reviewer session, or a reviewer that returned nothing. Storage admits `Failed -> Validating` only under that condition and the existing headroom check, in the same transaction that opens generation `n+1` (`candidate.validation_started` carries `revalidation: true`); the candidate revision, approval, plan hash, worktree and attempt count are unchanged, the checks run again and a fresh reviewer session starts, and the reviewer prompt names the generation (never the earlier reviewer's output). Nothing else qualifies: a failed, blocked, missing or interrupted check keeps its repair/retry path; any recorded verdict, passing or not, is review evidence and stays; a reviewer lost mid-turn reserved the remaining approved cost, which closes this gate exactly as it closes repair, so no new budget is ever granted. `GET …/candidate` reports the decision as `revalidate_allowed` and the desktop offers the control only then.

**Amendment (2026-10-21, candidate content and review evidence).** An audit found evidence that did not bind to candidate content, diffs that hid changes and refusals that changed no state. Each item below amends the point it names.

- *Point 2, generation reset.* Every validation generation resolves the leased worktree and verifies HEAD, tree and tracked content. It then removes every untracked and ignored path (`git clean -ffdx` with the work tree named explicitly) and records them in `candidate.worktree_cleaned`. Checks may still leave untracked output within a generation, but a later generation (resumption, re-validation) no longer inherits it. Tracked edits are never reset.
- *Points 2, 6 and 7, content drift.* The claimed generation detects a worktree that no longer holds the candidate: before or between checks, after them, after the review, or missing. The candidate then fails with a reason that starts `candidate content drift:` and names the changed paths, the check or review it followed, and the next steps (repair in a fresh worktree, or the next plan revision). Such a candidate is marked `content_drift` and point 7 excludes it, because its worktree is no longer evidence of the candidate. `POST …/validate` no longer answers drift with a 409 that records nothing. `GET …/diff` serves the frozen commit pair with a `worktree_drift` note instead of refusing.
- *Point 3, diffs.* Review and display diffs use `--text`, so `-diff`/`binary` attributes from the tree, `info/attributes` or `core.attributesFile` cannot turn source changes into binary patches, and `--ignore-submodules=none`, so configuration cannot hide a gitlink change. Content with a NUL byte or invalid UTF-8 becomes a one-line summary naming both blobs rather than lossy text. The reviewer receives whole file sections up to 256 KiB, every changed path with how it is shown (`text`, `summary`, `omitted`), a truncation notice, and `attention_paths` for changed `.gitattributes`, `.gitignore` and `.gitmodules`. A larger candidate is reviewed with that bounded diff instead of being refused without a state change. Candidate verification reads index listings up to 64 MiB, so large repositories validate.
- *Point 3, review consistency.* `changes_required` and `blocked` must name at least one finding, and a pass cannot carry a blocking finding. Finding paths must be relative, and every string must be bounded, non-blank and free of control characters (`schemas/review-result.schema.json` says the same; the reviewer's instructions state the verdict and path rules). Any other output is no verdict: point 7 re-validation applies, and automatic repair never spends an attempt on it.
- *Point 3, reviewer traceability.* `review.tool_call` events record the reviewer's tool calls with the tool name and `path` argument only. Failed or refused calls are marked `failed`, at most 256 per session. Rejected output is kept as the private artifact `<reviewer session>.stdout`, named with its digest in the failure reason and never given to a later session. The reviewer's conversation is still not persisted.
- *Point 4, repair evidence.* The evidence block is delimited by markers that carry a random per-prompt token, so check output cannot forge the end of the block. The wording points at the acceptance criteria that follow it.
- *Point 6, decisions.* `GET …/candidate` adds `validate_allowed` and `decision_reasons` (`validate`, `repair`, `revalidate`). Each reason is the refusal the route would give, or null, and is computed by the same storage gates; `repair_allowed` also applies the one-writer lease rule. Repository, host and component-source checks stay with the routes. Paths passed to Git and to the reviewer's scope guard drop the Windows `\\?\` verbatim prefix.

## Evidence and remaining gates

Synthetic Pi fixtures make failure/recovery paths deterministic; required checks execute real host commands. Current platform and real-provider evidence are listed separately in `FOUNDATION-STATUS.md`, including the `scripts/m3-smoke.mjs` genuine-provider run (OpenRouter, pinned Pi 1.3.0) that closed the provider exit on Linux. Native Mac/Windows service lifecycle evidence remains open. Publication, merging, native service packaging, distributed clients and multi-repository scheduling remain later milestones. The developer controls merging.

## Amendment (2026-10-21): accounting, restart recovery and repair provenance

An audit of the M3 implementation found recovery charging outages as stage time, reserving spend for reviewers that were never prompted, cost the budget never saw, and usage and failure reasons clients could not see. Points 4 and 5 are refined as follows; nothing grants fresh budget or relaxes a gate.

- **Restart charges only what was durably observed.** An active validation or review stage stamps a heartbeat (`stage_checkpoint_at`) every five seconds. Recovery charges an interrupted stage up to its last heartbeat plus one interval rather than up to the restart, so downtime cannot close the documented "validate again" path; a record without a heartbeat (written before this amendment) is still charged up to the restart.
- **Unknown review spend begins with a durable marker.** `review.prompt_sent` is written immediately before the reviewer prompt and `review.usage_settled` after `agent_settled`, once the final usage is charged. Recovery reserves the remaining approved cost budget only between the two, exactly as the live path's in-flight rule does; a reviewer interrupted before its prompt, or after it settled, is resumable like an interrupted check with a fresh generation. A reviewer recorded by an earlier runtime, which wrote no markers, stays conservative. Interrupted writers keep the conservative reservation of point 5.
- **Cost accounting covers what Pi reports.** Compaction (summarization) usage from `compaction_end` is charged with the session. A message or summary that reports tokens without a cost is not refused, since the cost budget is enforced against Pi's price table, but it is recorded once per session as `usage.cost_unreported` and reported as `cost_unreported`, so the gap is visible instead of silently counted as zero. The reviewer checks its budgets on every record but persists usage when a message completes, the session ends or a check fails, and a charge of nothing appends no `candidate.usage` event. The reviewer tolerates a provider error Pi retries itself (`agent_end` with `willRetry`) exactly like the writer; the verdict waits for `agent_settled`.
- **Usage is visible where decisions are made.** `GET …/candidate` reports `usage` for the whole workflow (writer attempts, validation and review) against `max_attempts`, `timeout_seconds`, `cost_usd_micros` and the confirmed `max_task_repairs`. `GET /api/v1/tickets/{id}` reports `usage` summed over every workflow of the ticket's plan revisions and the plan-creation response repeats it as `ticket_usage`. A new plan revision still carries its own approved budgets, approved by exact hash; what earlier revisions spent is shown to the approver rather than silently reset. No ticket-wide hard ceiling is added: that remains a developer policy decision.
- **Repair keeps its causes and provenance.** An automatic repair whose writer fails pauses with that writer's own reason (`automatic repair writer failed: …`), the repair gate's refusal when no further repair may follow (for example a spent budget and the re-plan requirement) and the candidate's earlier reason. Attempts keep the provider, model, host fingerprint, Pi version and trigger they were admitted with after they settle; automatic repair writers run on the validation request's provider and model, which `review.started` also records. A repair writer is told it starts from the previous candidate's commit and revision, and quoted check output names files relative to the repository root instead of the previous attempt's worktree. Repair-feedback redaction treats the extended credential names (vault sessions, `*_PASS`, `*_PWD`, `*_PAT`, `*_DSN`, webhook, connection-string and database URLs) as credentials, and URL credentials are taken from every variable, inherited or not.
- **Related scheduling guards (ADR 0008 points 2 and 4).** `POST /api/v1/tickets/{id}/plans` accepts an optional `idempotency_key`: the same key and request return the plan and workflow it created (200), a different request is 409 (storage migration 8, `plan_requests`). A new revision settles earlier `plan_ready` or `approved` workflows of the plan as `cancelled` with `plan.superseded`, since they can never be approved or scheduled again. One writer per repository is re-checked inside the transaction that admits a writer or repair, so a concurrent second workflow is refused with 409 and stays `approved`.

any of its workflows has a live writer, check, reviewer, attempt or owned lease,
