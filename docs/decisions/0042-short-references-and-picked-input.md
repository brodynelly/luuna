# ADR 0042: short references and picked input instead of copied identities

Date: 2026-10-23, merged 2026-10-26. Status: Accepted. Drafted as ADR 0040 (PR #21, commit `55d1166`) and renumbered when it merged, because [ADR 0040](0040-terminal-keymap-and-settings.md) (terminal key bindings) and [ADR 0041](0041-no-repository-ci.md) (no repository CI) landed first; commit messages and PR #21's text that say "ADR 0040" for short references mean this ADR. Amends [ADR 0020](0020-capability-catalog-and-tui.md) point 3 (the terminal's typed full-hash acknowledgment), the matching lines of [specs/feature-rust-tui-workbench.md](../../specs/feature-rust-tui-workbench.md) and [specs/feature-rust-tui-foundation.md](../../specs/feature-rust-tui-foundation.md), and [DESIGN-SYSTEM.md](../DESIGN-SYSTEM.md) principle 3 (identities shown whole); builds on [ADR 0037](0037-single-rust-terminal-client.md) (the Rust terminal client), [ADR 0040](0040-terminal-keymap-and-settings.md) (the keymap) and [ADR 0034](0034-owned-component-library.md) (`@luuna/ui`).

## Context

The runtime names records with generated identities (`ticket-<uuid>`, `plan-ticket-<uuid>`, `workflow-<uuid>`, `mem-<uuid>`, `approval-<uuid>`) and binds decisions to 71-character content hashes. The clients showed those identities whole wherever a record appeared and, in the terminal, asked for them back: every ticket, plan, run and memory argument took the complete id, memory corrections and deletions took the complete content hash, and approving a plan meant retyping its complete hash. The owner asked that nobody have to copy a generated hash or id to use any client, and that the desktop, its browser build and the terminal make records selectable instead.

The hash acknowledgment exists so that an approval names exactly the plan the developer reviewed. That property comes from the client sending the hash of the plan it displayed, and from the runtime refusing a hash that is not the plan's current one; the typing was the terminal's stand-in for the desktop's checkbox, not a separate guard.

## Decisions

1. **Short ids.** A generated identity's short id is the first eight hex digits of its UUID; an id without a UUID (a project slug, `plan-1` in fixtures) is its own short id. A plan's short id is its ticket's, because the runtime names a plan `plan-<ticket id>`. The terminal (`crates/luuna-tui/src/refs.rs`) and `@luuna/ui` (`shortId`, `shortHash`) compute the same value.
2. **References resolve before anything is sent.** In the terminal's command line and in workbench forms, a ticket, plan, run or memory argument accepts its full id, its short id, any prefix of at least four hex digits (optionally after the kind prefix, such as `ticket-3f2a`), or, for runs, `latest`. The client reads the same lists any developer could read (projects and their tickets, runs, the project's memory including user memory), picks the one record named and sends that record's exact id. An ambiguous reference is refused with the candidates' short ids and titles, an unknown one with a pointer to the list; neither sends a request. An argument not shaped like a reference passes through untouched, so nothing extra is read for it. A kind prefix must match the argument (`cancel ticket-3f2a` is refused, never matched against runs). The flags that take an id lists print, `runs --before` and `plan --memory`, resolve the same way. A workbench form resolves a reference among the records the workbench has loaded and sends that exact id, so the request, the workbench context and the record it then shows name one record; `latest` is offered only beside loaded runs. A reference nothing loaded resolves is sent as typed for the command to resolve or refuse, the context for it is cleared rather than kept as the reference, and a record read adopts the identity the runtime returned.
3. **Hash prefixes acknowledge only the hash just read.** A plan approval (`--acknowledge-hash`), a candidate hash (`--candidate-hash`) and a memory content hash accept the complete hash or a prefix of at least eight hex digits, with or without `sha256:`. The prefix is compared with the hash of the record the command has just read; a prefix that does not begin it is sent or compared as typed, so the existing exact checks refuse it. The complete hash is always what reaches the runtime.
4. **Interactive approval takes a word.** After displaying the complete plan and its complete hash, the terminal asks the developer to type `approve` (or `yes`, or a hash prefix). That word stands for the hash shown above it, as the desktop checkbox stands for the hash beside it. An empty answer cancels; nothing is prefilled or auto-submitted, and a terminal too small to show the plan still cannot approve. The client sends the hash of the plan it displayed.
5. **Lists lead with what a record says.** Terminal list output and workbench lists show short ids beside titles, scopes and states (`3f2a91c0  r1  missions  Greeting`, `workflow 8b1e0000 · plan 3f2a91c0 r2`, `[project] Use structured errors`); detail panes add a `Short id` line and keep the complete identity. `--json` output is unchanged. The plan's complete hash stays whole wherever approval is decided.
6. **Workbench forms offer choices.** A form field gets choices the workbench has already read, picked with Left and Right: repositories of the current project, projects, tickets and plans from the board, runs (and `latest`), memory records with their content, Orbit recipes, a run's tasks, plus the fixed values the runtime accepts (memory scopes, promotion targets, stack profiles, ticket purposes, task roles) and yes/no for every boolean option. Typing still works. Picking uses the keymap's `left` and `right` actions (ADR 0040), so rebinding or unbinding them moves or removes it, including their modified forms; inside a field, letters stay text. A required argument with exactly one possible record (the only repository) is filled in; scopes and runs are never chosen for the developer. After a scaffold proposal, the scaffold form carries that proposal's hash instead of asking for it.
7. **Desktop identities copy instead of being retyped.** `ShortId` in `@luuna/ui` shows a generated id or hash by its short form, keeps the whole value as its tooltip and accessible name, and copies the whole value on click. The desktop uses it for workflow, session, plan, approval, memory, candidate and reviewer identities; inside a row that is itself a button (Board cards) the short id is plain text. The task graph's "derived from advisory task" is a select of the advisory tasks of inspected runs of the selected ticket's own plan, leaving out a task whose id is also a task of the plan being built (the runtime refuses both other derivations), plus a value set by a proposal, and the registration form derives a repository id from the checkout's folder name until the developer types one.

## What does not change

Approval still binds to the exact immutable plan revision and hash, and the runtime still refuses a stale or mismatched hash. Memory corrections, deletions and promotions still send the exact expected hash. No route, request body or `--json` result changes, and no capability is added or removed; only the catalog's description of the approval acknowledgment and the help of `--acknowledge-hash`, `--candidate-hash` and the memory content-hash arguments now name the word and the prefix. Resolution reads only lists the developer may already read and grants nothing.

## Alternatives rejected

- **Prefilling the hash in the approval prompt**: one Enter would approve whatever was last loaded; a typed word after the displayed plan keeps the deliberate step without the copying.
- **Accepting the word `approve` on the command line**: a script has no displayed plan to stand for, so non-interactive approval still names the hash (a prefix is enough).
- **Runtime-side short ids or a lookup route**: the clients can resolve from existing reads, and a new route would change the catalog and the parity contract for no new capability.
- **Shortening the plan hash beside Approve**: the full hash stays the evidence the acknowledgment refers to.
