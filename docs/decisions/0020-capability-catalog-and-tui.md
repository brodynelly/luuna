# ADR 0020: one capability catalog, shared failure explanations and a terminal client

Date: 2026-10-21. Status: accepted. Implements the client-parity slice of M6 (R02, A19, A33); the publication, multi-repository and scaffolding actions of M4/M5/M7 join the catalog as they land.

## Context

R02 requires that the browser and the terminal expose equivalent product actions, and A33 that every client capability has an equivalent action and a consistent failure explanation in each client. Until now the desktop client (ADR 0001, ADR 0013) was the only client: its actions were spread over five React panels, the refusal and next-step text lived in `apps/desktop/src/failures.ts`, and nothing enumerated what "every product action" meant. Adding a second client by hand would have copied that table and drifted from it. The runtime's router (`crates/luuna-runtime/src/lib.rs`) is the only authoritative list of actions, and it changes with every milestone.

## Decision

1. **One catalog of product actions.** `schemas/capability-catalog.json` lists every action the clients expose, once: its runtime method and route, the `@luuna/api-client` method, the desktop control (a `data-capability` attribute value; a control that triggers several reads carries several values separated by spaces), the TUI command, the failure classes that apply, and, where the clients reach the same action differently, a note saying how. `schemas/capability-catalog.schema.json` is its contract. `scripts/check-contracts.mjs` (run by `npm test`) validates the catalog, requires unique ids, commands and desktop markers, parses the runtime's `.route(` declarations read-only and refuses a catalog entry whose route or method the runtime does not serve, checks that every `client_method` exists on `LuunaClient` and every failure mode is a shared class, and names every runtime mutation that no client exposes yet (`LUUNA_CATALOG_STRICT=1` turns that report into a failure once parity is complete).
2. **One source of failure explanations.** The pure logic of the desktop's `failures.ts` moved to `packages/api-client/src/failures.ts`: `describeFailure`, `nextStep`, `baselineStep`, `actionFailure`, plus `classifyFailure` and `explainFailure`, which return the failure class and the sentence `"<Action> refused: <reason> <next step>"`. The desktop re-exports it; the TUI imports it. Transport failures and 5xx stay plain sentences; a server body is never shown. The runtime still decides every state, permission, reason and refusal: the explanation only maps the runtime's recorded reason to the next step the runtime admits.
3. **A terminal client with parity.** `packages/tui` (`@luuna/tui`) is a Node client with no dependency beyond `@luuna/api-client`, built on `node:readline`. `luuna-tui` alone opens a keyboard-driven workbench (lists navigated with the arrow keys, Enter, Esc, `r` to reload, `q` to quit) whose menus are generated from the command table, so every cataloged action is reachable; authoritative state is re-read from the runtime after each action; `/health` is polled, an outage is shown in the header and every list reloads when the runtime answers again. `luuna-tui <command> [args] [--json]` runs one catalog action for scripts and tests. The connection comes from `LUUNA_URL` (loopback only) and `LUUNA_API_TOKEN`, prompted hidden on a terminal and never echoed. Approval requires the developer to acknowledge the complete plan hash (typed, or `--acknowledge-hash`), exactly as the desktop checkbox stands for the hash shown beside it; a mismatch is refused before anything is sent. Run events are followed live over the runtime's SSE stream with `Last-Event-ID` resumption (`LuunaClient.streamEvents`/`followEvents`), reconnecting after an outage from the last received sequence and ending when the run settles.
4. **Parity evidence.** `packages/tui/test/commands.test.mjs` proves that every catalog entry has one command and that each command issues the cataloged method and route against a mocked fetch; `apps/desktop/src/capabilities.test.ts` proves that every catalog id is carried by a desktop control and that every marker is cataloged; `scripts/tui-smoke.mjs` drives the documented walkthrough through the TUI against a built runtime and the synthetic Pi fixture (import, discovery, confirmation, baseline, ticket, plan, exact-hash approval, writer, candidate, diff, validation with `fixture:review_malformed_once`, re-validation, a hard kill during a held check with the outage and the reconnection observed by a live follower, restart, recovery, orderly shutdown) and asserts that the TUI reports the same authoritative states the runtime's API shows, writing `report.json`/`report.md` outside Git.

Adding a product action costs one catalog entry (the contract check refuses a route the runtime does not serve), one `LuunaClient` method, one `data-capability` marker on the desktop control and one object in `packages/tui/src/commands.mjs` with its `example`; the three parity tests then cover it without further changes.

## Consequences

The desktop gained two small controls so that every cataloged action has a control: "Show writer attempts" on a ticket and "Stop runtime" (ADR 0010) beside Disconnect. The design system (ADR 0013) is untouched; the TUI shows every state as the runtime's unchanged text, as the design system requires, but had no tones until the third amendment added the terminal colour mapping of the same six tones. The `@luuna/api-client` source is loaded by Node directly (type stripping), so it uses no TypeScript syntax that needs transformation (no parameter properties, no enums) and imports its own modules with `.ts` extensions.

`npm test` fails when a catalog entry names a route the runtime does not serve, a client method that does not exist, a failure class that is not shared, a TUI command that is missing or an action no desktop control exposes. It does not yet fail for a runtime mutation that no client exposes: those are reported, so that M4/M5/M7 routes can land in the runtime first.

## Amendment, 2026-10-22

A green catalog check established wiring, not behaviour: an entry proved a route, a client method, a marker and a command existed, not that the desktop sent every registered repository, baselined every repository, sent a task graph, or offered a resume control in the states ADR 0017 admits; and the catalog could not establish the ticket-edit and memory obligations of `docs/06-memory.md` while the runtime served no such routes. [ADR 0026](0026-ticket-and-memory-controls-and-client-parity.md) adds those routes and controls, gives every entry a `required_by` trace, makes `scripts/check-contracts.mjs` map a fixed list of required actions to entries with both clients wired, moves the registration and plan request builders into `@luuna/api-client` so both clients send one body, and makes the TUI command test and the desktop tests assert request bodies and state-specific controls rather than marker presence. Adding a product action now also costs its `required_by` list; a state-specific control of an existing action (for example `Resume task` beside `Implement`) carries the action's existing marker, and `apps/desktop/src/capabilities.test.ts` allows several markers per action.

## Amendment, 2026-10-22 (later the same day): projections beside actions

The experience surfaces of docs/09-experience.md that [ADR 0027](0027-v1-advertised-scope.md) point 4 requires are projections of existing routes, not product actions, so they take no catalog entry: `packages/tui/src/commands.mjs` gains a separate `PROJECTIONS` table (`home`, `board`) whose entries name the catalog ids they read (`projects`, all `GET`), are reachable by name and from the interactive main menu, and print the shared projections of `packages/api-client/src/projections.ts`; `commandsByName` covers actions and projections, `commandsById` actions only, and the parity test keeps `COMMANDS` equal to the catalog while checking that every projection reads cataloged actions only. The desktop marks a surface with `data-surface` (`home`, `board`, `help`, `editor-handoff`), and `scripts/check-contracts.mjs` traces each required surface to the entries it projects, the desktop panel and the TUI projection (`REQUIRED_SURFACES`), beside the required-action traces that now also cover the testing-setup prerequisite (ADR 0022) and delegated roles with overrides (ADR 0023). A state-specific variant of an existing action keeps carrying that action's marker: the testing-setup offer's `Create the testing-setup ticket` control carries `tickets.create`.

## Amendment (2026-10-22, third): interactive mode audited

[ADR 0027](0027-v1-advertised-scope.md) point 5 makes an audit of the interactive mode a required v1 deliverable: `scripts/tui-smoke.mjs` proves the command mode only, and nothing had driven the menus with real keypresses in a real terminal. `scripts/tui-interactive-audit.mjs` now does, with the same options, environment and fixture conventions as the smoke (`--runtime <built luuna-runtime>`, `--out <dir>`, `--keep`, the synthetic Pi fixture, a fixture repository created under `--out`), and it writes `report.md`/`report.json` with every check as PASS/FAIL and the captured pane text as evidence.

**How it works.** The harness runs `luuna-tui` (no command) inside detached tmux sessions on a dedicated socket (`-L luuna-audit`, killed at the end, so no other tmux session is touched), sized with `new-session -x <cols> -y <rows>`, so raw-mode keypresses, `stdout.columns`/`rows`, the alternate screen and the cursor are real; the token reaches the client through tmux's `-e` environment, never through a command line. It sends keys with `send-keys` and reads the pane with `capture-pane -p` (`-e` for SGR attributes, `-J` to join wrapped rows, `-S -` for the scrollback) and the pane's cursor, alternate-screen and history state from `display-message`. Tone checks compare SGR parameters, because tmux re-encodes attributes when it captures.

**What it covers.** At 80x24: the Workbench renders with the connection header (success tone), the cursor on the first item and the help footer on the last row; Down/Up move the cursor; Enter opens Projects and Esc returns; Registration is driven through its prompts (name, repository id, root path, the empty line that ends the further-repositories list) and the result screen shows the runtime's observation, which the API confirms; the project is listed (`unconfirmed` in the attention tone) and its screen offers tickets, runs and every project action; the Discovery result scrolls (`lines x–y of n`, Down one row, PageDown one page, End, Home); the manifest is confirmed from a typed path; the baseline starts from a prompt and `r` reloads the project's run list in place until the run reads `completed` (neutral tone), as the API records; the baseline listing paints `passed` in the success tone; a ticket is created through the title, intent and criteria prompts and its list and screen open through the menus. At 40x24, 60x24, 80x12 and 40x12: the main menu fits (header first, footer last, no row wider than the pane, cursor inside, no scrollback), Down past the visible items scrolls the viewport with the cursor row visible and the position in the footer, and a text screen wraps its rows to the width while keeping its lines footer. With every client open, the runtime is hard-killed: each shows `RUNTIME OUTAGE` in its header within the poll interval, in the interrupted tone (never danger), truncated to its width without overflow; after a restart each header clears with the notice that the view was reloaded. The six tones render as six distinct SGR colours in a terminal through the real formatter, degrade to plain text with `NO_COLOR` set and when stdout is not a terminal, and the same baseline listing is painted on a terminal and plain when piped. `luuna-tui` without a command and without a terminal prints the help and exits 2. Finally `q` in every client exits 0, `stty -a` in the same pane shows canonical mode, echo and signals restored, the alternate screen is left, the cursor is shown and no escape byte follows the exit line. Not covered: screen-reader output (there is no terminal screen reader in the fixture environment), mouse input (none is implemented), and the approval, writer and publication actions, which the command-mode smoke proves with the same command table the menus use.

**What it found, and what changed in `packages/tui`.** The first run of the harness against the previous workbench found, at 40x12, every row longer than the pane wrapping (the catalog titles alone were up to 120 columns), the header and the first items scrolled out of the pane (23 rows of scrollback), the help footer out of view, and an empty first row from the clear sequence joined with a newline; at 80x24 menus of 25 items had no viewport; a result screen with a long path or JSON line wrapped past its footer; a prompt's question was written under the footer, scrolling the frame away (and readline's `question` erases everything below the cursor, so no hint can live under it); a running action (for example `follow`) could not be left with `q` or Esc because keys were ignored while busy; there were no tones. The harness itself had to learn three tmux facts worth recording for whoever extends it: `capture-pane` trims trailing spaces from rows, a row written at full width keeps the terminal's "wrapped" flag left by an earlier echo unless the row is erased whole (`ESC[2K`) before it is written, and output longer than the pane leaves the visible capture, so exit lines are read with `-S -`. The workbench now draws exactly `rows` rows on the alternate screen with the cursor hidden (both restored on exit, together with raw mode): every row is truncated to the width with an ellipsis (`src/text.mjs`: `truncate`, SGR-aware, wide characters counted twice) or, on a text screen, wrapped at the last space that fits (`wrap`, colour closed at each row end and reopened on the next, so the `lines x–y of n` footer counts terminal rows); menus scroll behind a viewport that keeps the cursor visible and name their position in the footer; the footer shortens its wording to fit (`↑↓ Enter r Esc q` at 40 columns) and never loses `q`; the key hint of a prompt sits on the notice row above the question; a resize re-renders; `q` and Ctrl-C quit from anywhere, Esc aborts a running action through its `AbortSignal`, and Ctrl-C inside a prompt quits instead of hanging readline. Menu items show the command's short action label with its name and the catalog title as detail, and result screens are titled `<Action> (<name>)` so the name survives narrow widths. The six tones of ADR 0013 exist in `src/format.mjs` as the same tables as `apps/desktop/src/design/tone.ts` (`runTone`, `candidateTone`, `checkTone`, `baselineTone`, `verdictTone`, `severityTone`, `leaseTone`, `connectionTone`), painted as one SGR colour each (green, cyan, rose/red, amber/yellow, dim, plum/magenta) around the runtime's unchanged word only when `colourEnabled` says so (a terminal, `NO_COLOR` unset or empty, `TERM` not `dumb`); the command mode passes it through `io.colour` and `--json` output is never painted. `packages/tui/test/text.test.mjs` and `format.test.mjs` pin the helpers and the tables. The parity tests and `scripts/tui-smoke.mjs` are unchanged and still pass.

## What remains

- Parity for later actions: the scaffolding proposals and scaffolds of ADR 0019, the publication, publication record and reconciliation of ADR 0018, the memory promotion and project export of ADR 0021 and the multi-repository task listing of ADR 0017 were cataloged the same day with their client methods, desktop controls and TUI commands (49 actions); `scripts/check-contracts.mjs` names any later runtime mutation until it is cataloged.
- The keyboard audit and the terminal tones of the interactive TUI exist (third amendment); screen-reader friendliness of the list output is not audited, because no terminal screen reader runs in the fixture environment.
- The browser client of P61 is the desktop's web build; it shares the desktop markers and needs no separate catalog work, but its own smoke evidence belongs to M8.
