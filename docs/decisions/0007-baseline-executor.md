# ADR 0007: supervised check execution and baseline-bound implementation gate

Date: 2026-10-17. Status: accepted; amended 2026-10-21 (evidence hardening, below).

## Context

M2a records confirmed check recipes but executes nothing, and the storage layer rejected `Implementing` with a placeholder guard. R08 requires a usable testing setup and a passing baseline before feature work, and the validation chapter requires evidence that binds to recorded commits, environments and artifacts rather than to a model's claim.

## Decision

1. **A recipe is an executable plus an argument array.** `luuna-executor` resolves the executable on `PATH` or as a repository-relative file under the registered root, verifies declared host capabilities against installed tools, runs in an explicit directory that must stay inside the root, applies the recipe's deadline, and owns the whole process group (Unix) so cancellation and timeouts reap descendants. The child, and every version probe, receives a cleared environment with Luuna configuration, `GIT_*` variables and anything credential-shaped removed. A descendant that keeps the output pipes open after the command exits is given a short grace, then the whole group is terminated and the check fails rather than hanging; cancellation and the deadline remain the recorded status whatever happens to capture. Windows has no process group here, so only the direct child is killed and a surviving descendant is named in the result's reason. Artifact directories and logs are created private (0700/0600 on Unix) whatever the parent directory or umask allows. Native execution keeps host permissions; the container profile is recorded as blocked until an isolation mechanism exists.
2. **Every outcome is deterministic runtime evidence.** Exit 0 is `passed` only when no recognised test runner reported an empty suite; any non-zero exit, deadline or signal is `failed`; a missing executable, incapable host, dirty checkout, container profile or empty suite is `blocked`; cancellation and runtime restart are `cancelled` and `interrupted`. Output streams into bounded private artifacts whose SHA-256 digests are part of the record, and only short excerpts enter the event stream.
3. **A baseline is a run.** It uses the shared run lifecycle, durable events, replay, SSE, cancellation and restart interruption. It binds to a `BaselineIdentity` (manifest hash, repository, exact HEAD commit and tree) whose hash is each result's `candidate_hash`, and to an environment fingerprint derived from the resolved executables and their versions. A checkout with uncommitted changes is not an exact commit, so its baseline is blocked rather than measured, before any probe runs; the checkout is inspected again after the last check, and a pass is withheld (the baseline fails) if HEAD moved, any tracked file was modified or the identity changed while checks ran; untracked files a check creates (build caches, reports) do not change the recorded commit or tree and are recorded in a `checkout.untracked` event instead; Luuna-owned worktrees (M2c) will remove that limitation.
4. **Implementation is entered only through `begin_implementation`.** Inside one write transaction it re-reads the durable approval, the bound plan, the project's current confirmed manifest and the latest baseline for every repository in the plan, and requires each baseline to be passed, bound to the plan's manifest hash and base commit, and recorded with the same environment fingerprint. Each required recipe must have its own passed result bound to the baseline's candidate hash, commit and fingerprint (optional results never count either way), and the baseline's run must have settled as `completed`; startup recovery interrupts a passed verdict whose run never settled, so the verdict/run crash window cannot authorize a writer. The placeholder guard is gone; a direct `Implementing` transition remains rejected.
5. **Artifacts are addressed by record identity.** `GET /api/v1/runs/{id}/artifacts/{recipe}.{stdout|stderr}` serves the private log for a run the caller is authorised to see; no request names a filesystem path.

## Consequences

`POST /api/v1/projects/{id}/baselines` and `GET /api/v1/projects/{id}/baselines` implement the baseline part of R08. Required recipes decide the verdict; optional recipes run on request and are recorded without affecting it. Empty-suite detection covers cargo, go, pytest and vitest/jest summaries and is a floor, not proof that a suite is meaningful. The first approved writer, worktree ownership and revalidation at scheduling time remain M2c.

## Amendment (2026-10-21): evidence hardening

An audit found checks whose evidence overstated what ran or what the executor contained. These rules now hold for baseline and candidate checks alike:

1. **Nothing a check started outlives its result.** After the direct child exits normally and its output drains, the executor terminates whatever is still in the check's process group (a server started with redirected output, a daemon) before the result is recorded, names it in the execution's `reaped_descendants`, and the runtime appends `check.reaped`. A descendant that called `setsid` left the group and stays out of reach without a sandbox. On Windows each check is assigned to a kill-on-close job object right after spawn, so cancellation, deadlines and the post-exit reap end the tree, and the operating system ends it if the runtime dies; processes the child starts before assignment escape. This path is compile-checked for Windows and macOS but has not been executed on those hosts. Where a tree is not contained, the recorded reason says that only the direct child was terminated instead of claiming the group was.
2. **Process groups survive a hard kill only until restart.** Every check, baseline or candidate, records `check.spawned` with its `process_group`: group ID, the leader's start time (Linux boot ID included) and a per-execution marker exported as `LUUNA_CHECK_GROUP`. Before startup recovery interrupts the runs, the runtime reconciles each recorded group: survivors are terminated only when verified as that check's (the leader alive with its recorded start time, or on Linux the marker in a member's environment), never on a matching ID alone, and are named in `check.orphans_reaped`; processes that may belong to the group but cannot be verified are left alone and named in `check.orphans_unverified`. On macOS the reconciliation relies on the leader's start time and is compile-checked only.
3. **An empty suite is judged on executed tests.** Runner summaries (cargo, go test, pytest, jest, vitest, unittest, Gradle test tasks) are parsed from every line of both whole output streams while they are captured, not from the size-capped artifacts, and count executed tests only. A recognised summary reporting that nothing executed (no tests, all skipped, ignored or deselected, `[no tests to run]`, `NO-SOURCE`) blocks an exit-0 check as an empty suite; a line that merely resembles a summary (`Tests passed!`) is not one. `Artifact.retained_bytes` records what the digest covers next to the stream's total `bytes`.
4. **Missing infrastructure is blocked, not failed.** An executable that cannot be found or started is blocked as before. A repository-relative executable that does not exist (`node_modules/.bin/...`, `.venv/bin/...`), exit status 127, a shell's "command not found", Python's `ModuleNotFoundError` for a module that is not in the repository, or an unresolved bare Node package is recorded as `blocked` with a reason that asks for a dependency-preparation recipe (for example `npm ci`) ordered before the tests in the manifest; a name the reason quotes from check output must look like a name and is withheld when it is credential-shaped, because check reasons reach model prompts; candidate checks run in a fresh worktree without ignored files such as `node_modules/` or `.venv/`, so the developer checkout's installed state is not evidence for them. Automatic repair never treats such a result as actionable. A required candidate check that the remaining workflow time ends before its own deadline is `blocked` with a "workflow time budget exhausted" reason, and the candidate pauses with "workflow time budget exhausted during required checks; re-plan required".
5. **Fingerprints describe the toolchain the recipe runs.** Version probes run in the recipe's working directory (where rustup, asdf, mise, volta, pyenv and corepack select a version), with the same sanitised environment, in their own process group; `go` is probed with `go version`. A probe that cannot start, times out or exits non-zero records no version and its failure becomes part of the fingerprint, so a baseline recorded when a probe failed (or from another directory) no longer matches and must be re-run.
6. **Resolution and naming are platform-safe.** On Windows a bare executable name is resolved only with the startable `PATHEXT` extensions in `PATHEXT` order, never as the extensionless POSIX shim Node, npm and Flutter install beside their `.cmd`/`.bat` files; on Unix a `PATH` entry must be executable; empty and relative `PATH` entries are ignored. Artifact files for recipe IDs with upper-case letters or a Windows device stem (`nul`, `con`, `com1`, ...) get an escaped, digest-suffixed name, so IDs that differ only in case never share a log on case-insensitive filesystems.
7. **Credential stripping covers more shapes.** Besides the earlier markers, vault sessions (`BW_SESSION`, `OP_SESSION_*`), `*_PASS`, `*_PWD`, `*_PAT`, `*_DSN`, webhook URLs, connection strings and database URLs are withheld from checks and probes; `is_credential_name` is exported for repair-feedback redaction, whose token-shape line removal now uses the executor's `line_carries_token` (per-format minimum lengths, so a real `AKIA` key ID matches, plus GitHub app, Stripe live, npm, Hugging Face, PyPI and Slack app tokens, `Authorization: Basic|token`, `aws_secret_access_key` and `_authToken=` lines); it stays best effort (ADR 0009). Repair feedback opens each log under the file name of point 6 above.
8. **Baselines are exclusive and settle.** A second baseline for a repository whose baseline run is still active is refused with 409 naming that run (storage refuses a second running record in the same transaction). Baseline results record `artifact_refs` and `artifact_hashes` keys as `{recipe}.{stdout|stderr}`, the identity decision 5 serves (earlier records keep their `artifact:` refs). A failure to persist a result or the verdict settles the baseline as failed, retried once, instead of leaving it `running`. A dirty checkout's blocked reason names the paths; when only untracked files block it, the reason says they may be an earlier check's output and that adding them to `.gitignore` resolves it, because Git-ignored files never block a baseline. Baselines still run in the developer checkout.
