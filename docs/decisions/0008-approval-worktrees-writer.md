# ADR 0008: exact approval, Luuna-owned worktrees and one scoped writer

Date: 2026-10-17. Status: accepted.

## Context

M2a records confirmed manifests and M2b records baseline evidence, but no run could modify a repository and no API exposed plans or approvals. The handoff for M2c asked for exact plan approval through the API, revalidation at scheduling, Luuna-owned worktrees with durable ownership, and one bounded writer whose scope and budgets are enforced by the runtime rather than promised by a prompt. ADR 0003 allows a temporary local ticket before the Missions adapter exists; ADR 0005 fixes the canonical ticket route.

## Decision

1. **The ticket is a temporary local record.** `POST /api/v1/projects/{id}/tickets` creates a revisioned SQLite ticket whose `source` is `luuna_sqlite_temporary`, idempotent per project and key, scoped to registered repositories. Plans bind to `ticket_id` and `ticket_revision`; revising a ticket makes every earlier plan stale and scheduling refuses it until re-planned. The Missions adapter (M6) replaces this source behind the same binding; identifiers and revisions are preserved, and no second writable authority is introduced in the meantime.
2. **The runtime builds plans; clients only describe tasks.** `POST /api/v1/tickets/{id}/plans` takes a task (repository, paths, operations, optional criteria), optional permission prefixes and budgets. The runtime fills the project, the ticket revision, the current confirmed manifest hash, that manifest's recorded base commit, the manifest's recipes as the required checks, `max_workers = 1`, and seals the hash. Each submission is the next immutable revision and opens a workflow run already bound to it (`plan_ready`).
3. **Approval names one exact hash.** `POST /api/v1/plans/{id}/approvals` carries the revision, the hash the approver saw and who approved; permissions are copied from the plan so a client cannot widen them. A different hash, a newer revision or a workflow not waiting for approval is refused.
4. **Scheduling revalidates everything before any state changes.** `POST /api/v1/runs/{id}/implement` requires an `approved` workflow, recomputes the host's environment fingerprint from the manifest's required recipes, re-inspects the repository and refuses a moved HEAD or changed identity, refuses an active lease on the repository (one writer per repository), refuses an exhausted attempt budget, and only then calls `Store::begin_implementation`, which in one transaction re-checks the durable approval, the ticket revision, the current manifest hash and its recorded base commits, and a passed baseline per repository whose run settled as `completed` and whose required recipes each have a passed result bound to the baseline's candidate hash and commit. Any failure leaves the workflow `approved` and returns 409 or 422 with the reason.
5. **Writers work only in Luuna-owned detached worktrees.** The worktree lives under the private data directory (`worktrees/<run>/<attempt>/<repository>`), is created at the planned base commit and verified, and is recorded as a lease in the database with a unique active lease per repository. `git worktree add` writes bookkeeping under the developer repository's `.git/worktrees` and the candidate's objects into its shared object store; the developer's files, index, HEAD and branch are never touched, which tests assert byte for byte. Worktrees are preserved on success, failure, cancellation and restart; startup recovery marks leases of interrupted runs `abandoned` and running attempts `interrupted`.
6. **Scope is enforced twice, and neither is an OS boundary.** Pi runs with only the built-in file tools the task's operations allow (`read`, `grep`, `find`, `ls`; `edit`, `write`), with resource discovery, sessions, MCP, skills and context files disabled, and with the Luuna scope guard loaded explicitly. The guard blocks every tool call outside the leased worktree (resolving symlinks in the existing prefix) and every write outside the task paths. After the session the runtime lists the worktree's changed paths with `git status` and rejects the attempt if any path, including both ends of a rename, is outside the task's paths or the approved permissions. Only an in-scope, non-empty change set is committed by the Luuna writer identity and recorded as a `CandidateSet`; the workflow then enters `validating`, the next gate (M3). Native execution keeps host permissions: a hostile model could still reach what the account can reach, and the documentation says so.
7. **Budgets fail closed.** Attempts count against `max_attempts` durably; `timeout_seconds` is the session deadline; provider-reported cost is compared against `cost_usd_micros` on every event; `max_workers` is one. Exceeding any of them stops Pi, fails the attempt, releases the lease and preserves the worktree.

## Consequences and validation

Tests cover: idempotent and conflicting ticket creation; plan binding to ticket revision, manifest hash and base; stale approval after a new revision; missing or stale baseline; a changed recipe (new manifest); a moved HEAD; an unrelated repository; a second writer; cost, attempt and empty-result budgets; out-of-scope changes rejected with the worktree preserved; cancellation reaping Pi and preserving the worktree; restart abandoning the lease and interrupting the attempt; and a full in-scope writer whose candidate commit is authored by the Luuna writer while the developer checkout is byte-identical. The scope guard's path logic has its own Node tests. Genuine evidence with the pinned Pi and a real provider is recorded in the status report. The dirty-checkout limitation on baselines remains until baselines also run in leased worktrees.
