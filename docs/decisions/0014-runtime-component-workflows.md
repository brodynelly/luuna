# ADR 0014: explicit managed component workflows and approved context

Date: 2026-10-21. Status: accepted for the owner's requested runtime integration. Implements the ticket authority boundary of ADR 0003 and the runtime adapters deferred by ADR 0012. Existing approval, baseline, candidate and publication decisions remain in force.

## Context

The public `luuna-missions`, `luuna-atlas` and `luuna-beacon` repositories are already consumed as exact-commit submodules. Installing or smoke-testing those CLIs does not make the application use their records. The owner requested actual ticket, memory and prompt workflows through Luuna without importing development history, exposing personal stores or weakening exact-plan authorization.

## Decision

1. **Activate explicitly per project.** `GET /api/v1/projects/{id}/components` reports state; `POST` to that route initializes the three stores and migrates legacy tickets. The durable `initializing` state freezes affected ticket actions until activation is reconciled and becomes `enabled` only after successful initialization and migration. Component discovery alone never changes an existing project's authority. An enabled project fails closed if its pinned toolchain or managed store is unavailable; there is no silent SQLite fallback.

2. **Use managed private stores.** Each project uses `<data_dir>/components/projects/<project_id>`. Explicit user-scoped memory uses `<data_dir>/components/user`; project/process memory stays in the selected project's workspace. Existing developer checkouts, imported `.seeds`/`.mulch`/`.canopy` directories, user Pi state and personal memory are never adopted automatically. Compatible component data formats, JSON APIs, CLI aliases and upstream notices remain intact. Luuna invokes the public CLIs and does not mutate their internal files directly.

3. **Missions owns enabled ticket intent.** The canonical creation route remains `POST /api/v1/projects/{id}/tickets`. A compatible Missions description contains a versioned Luuna envelope with immutable Luuna ticket/project identity and editable intent, acceptance criteria and registered repository IDs; the ordinary Missions title, status and dependencies retain their meanings. SQLite keeps a revision-aware projection, immutable original delivery intent, source identity/fingerprint and Luuna's execution state. It cannot independently edit Missions-owned fields. Initial migration preserves Luuna ticket IDs, numeric revisions and creation timestamps; existing plans and approvals remain durable.

4. **Reconcile external edits explicitly.** Ticket GET/list routes return the last reconciled projection so a client can still display a stale ticket and offer recovery. `GET /api/v1/tickets/{id}/source` observes authoritative source identity, fingerprint, status and reconciliation need. `POST /api/v1/tickets/{id}/reconcile` requires `{expected_revision}`. A changed source or direct dependency snapshot advances the projection revision, including status/dependency changes that leave visible intent unchanged; a stale expected revision is refused. Planning, approval, implementation, repair and candidate evidence consumption re-observe source freshness. Closed tickets and unresolved dependencies block work. Reconciliation never renews an old plan's authorization: changed revisions require a new plan and approval. The current slice intentionally has no Luuna ticket-edit endpoint because the existing component CLI offers no atomic cross-process optimistic edit contract.

5. **Persist before external side effects.** Ticket creation reserves original content and records that delivery started before invoking Missions. A stable label and the envelope identity allow lookup of an uncertain successful create before acknowledging or retrying. Duplicate identities, changed reserved content, or an attempted delivery with no recoverable identity fail closed instead of creating another issue. The Atlas/Beacon operation ledger similarly binds a project/request key to original content and reconciles uncertain writes. Recovery may require restoring an externally removed identity or inspecting the managed source; retries do not invent new authority.

6. **Select memory and prompts as exact plan inputs.** Atlas-backed memory has explicit project/process/user scope and provenance. User scope requires explicit retrieval/selection. Only records bound by Luuna are returned as application memory; arbitrary imported records do not enter context. Beacon prompts have a current version and rendered-content hash; updating an existing name requires its expected version. The application previews and selects resources, then the runtime stores their exact content, provenance, versions and hashes in optional `component_context` inside the canonical immutable plan. The complete plan remains visible before exact-hash approval. At approval and execution boundaries the runtime resolves the selected records again and refuses changes, deletion or scope drift. Only those approved snapshots become bounded worker resources; component text never grants authority to skip runtime rules. Omitting `component_context` preserves existing plan hashes and the legacy workflow.

7. **Supervise a bounded native process boundary.** `luuna-components` verifies the committed manifest, `.gitmodules`, Git HEAD/index gitlink, clean component checkout, package identity/aliases and Bun 1.4.3 before invoking the pinned TypeScript entrypoint. A fixed bridge receives bounded JSON on stdin and starts the actual CLI with explicit arguments and no shell. Processes receive an allowlisted environment, isolated HOME/config, disabled Bun `.env` loading/automatic installation and Git discovery/config controls. Links/reparse points in workspace ancestors and component stores, plus configured executable Atlas hooks, are refused. Each process has a 30-second deadline, 1 MiB input, 4 MiB stdout and 64 KiB stderr bounds; owned descendants are stopped through Unix process groups or a Windows Job Object. Arguments and child output are not reflected in API errors. These are native host processes with host permissions, not an OS sandbox.

## Consequences and validation

The application now has real component adapters while retaining explicit activation, legacy compatibility and immutable approval. Source inspection is deliberately conservative: external mutations after a freshness observation cannot be made atomic with a SQLite transaction by the current CLI API; subsequent runtime boundaries re-observe and refuse drift. Missions delivery searches only the selected identity and reads known source/dependency snapshots through public commands; at most 64 direct dependencies and 10,000 identity-search matches are accepted. Oversized or malformed contracts fail visibly rather than truncate.

Focused storage tests cover migration identity, restart durability, idempotency, projection-only writes, stale revisions and old-plan invalidation. Explicit real-component tests exercise actual Bun/CLI migration, external edits, dependencies, reconciliation, removed-marker recovery, duplicate/uncertain writes and unavailable integrations in disposable private stores. The runner's real test covers all three CLIs, a large ticket, Atlas CRUD/search, Beacon version changes and executable-hook refusal. Commands, platforms and observed results are recorded in [FOUNDATION-STATUS.md](../FOUNDATION-STATUS.md#runtime-component-workflows-october-21-2026).

Synthetic Pi remains synthetic even when ticket/memory/prompt storage uses real component CLIs. A passing browser smoke does not establish native Tauri UI behavior or a new genuine-provider exit. Browser/TUI parity, broader memory policy/retention, packaging and supported-platform evidence remain full-v1 obligations; publication and developer-controlled merging remain separate gates.
